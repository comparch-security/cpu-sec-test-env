Architecture

The environment is a single dispatcher around one mutable workdir. The Makefile is the entry point (make ARCH=<lane> …); it reads the few values its recipes need from env.sh and dispatches to scripts/<lane>/ (the x86_64 lane is implemented inline in the Makefile). The benchmark submodule is the shared resource every lane mutates in turn — which is why every lane entry point takes a lock.

The lane lock

Every lane entry point that mutates the bench worktree — the run and clean paths, and the corpus-staging deploy legs — takes an advisory flock on build/.lane.lock and writes the lane name into it; a second concurrent lane fails fast with lane busy: <holder> holds build/.lane.lock (dump is the deliberate exception: it takes no lock). The lock file is opened append-style by the Makefile and by every lane script, so a contender's open never wipes the holder's name before the contention check reads it, and the name is written only after the lock is held. The aarch64 run recipe takes the lock once around both legs (prepare and run) and passes LANE_LOCK_INHERITED=1 to the two scripts; a script honours that marker only when the inherited descriptor verifiably is the held lane lock — /proc/self/fd/9 must resolve to the lock file and a non-blocking flock on it must succeed — and then closes the descriptor so no lane child (scheduler, emulator, corpus binary) inherits it. A spoofed marker without the held lock dies.

Every lane run body is wrapped in an EXIT trap that, on every outcome except a timeout, collects the lane's artifacts into results/<lane>/<UTC-stamp>/, runs make -C benchmark clean and asserts the submodule is clean. A run that hits its timeout (exit 124) aborts without publishing anything.

Pins

All pins live in env.sh: the bench commit, the toolchains, qemu, the guest kernel and busybox, the NEMU checkout and commit, cheribuild and the CHERI images, the roots and the timeouts. The Makefile and the lane scripts read them; nothing else hard-codes them. The Makefile refuses to run with an empty timeout or an empty build root rather than let a shell command fail at the wrong moment; the submodule's HEAD is asserted equal to the pinned bench commit at every point the worktree is about to be consumed — the x86_64 deploy, the aarch64 lanes' prepare and run scripts, the shared corpus staging orchestrator, and the riscv64-nemu lane's deploy and run, which additionally re-check the submodule's cleanliness alongside the NEMU checkout's own pin. A git that fails never reads as a verified pin: every one of these checks captures its exit status and refuses, naming the unverifiable state.

Deploy and corpus staging

The system lanes' deploy stages what their run needs: the riscv64 lane builds a byte-reproducible kernel + busybox + rootfs image, and the CHERI lanes build their emulators and pinned disk images (a cold deploy is a world build); the host lanes' prepare builds only the scheduler, and the corpus is compiled on demand during the run. Every system lane's corpus is staged by one orchestrator, scripts/common/stage_corpus.sh: it copies the bench tree into a scratch tree under the lane's build/ area and drives the pinned bench runner's corpus mode there — the runner owns corpus keying and skip handling, so this repository never re-derives keys or rewrites skip tokens, and the staged tree carries the bench's tracked configure.json verbatim. scripts/common/corpus_manifest.py then verifies the staged set against the tracked registry (the registry's units minus the rows whose skip names the lane's token) and writes manifest.json: the corpus as staged, the per-unit digests, the side and support files, and the skipped records with their declared reasons. The riscv64-nemu lane stages through the same orchestrator and boots the image the absorbed venue package (scripts/riscv64_nemu/venue/) assembled; its completeness gate compares the run's record set against the staged verbatim registry.

The opcode-extraction shim

The bench's per-function opcode extraction disassembles a freshly built binary with an objdump. Every lane whose scheduler builds cross-target units puts a shim directory first on PATH (scripts/common/shim.sh) so that call resolves to the lane-appropriate cross tool rather than the host's single-target binutils; the CHERI lane points the same shim at the CTSRD SDK's CHERI-capable riscv64cheri-objdump, whose bin directory is deliberately off PATH.

Results and provenance

Each published stamp carries results.json and results.dat (the scheduler's record set and its report), versions.txt — the host-provenance record: the env.sh pins, the dpkg versions of the prerequisite packages, the host uname, the bench checkout (bench-head: and bench-tree:, the commit and a dirty-aware describe, with an unavailable sentinel when git itself fails) and the run's outcome (run-status: ok, or failed (rc=N) from the collector's own final rc) — and lane-specific extras (runtime variables, boot logs, guest status). On the host lanes the collector treats results.json and results.dat as required and parseable — absence, emptiness or malformed JSON fails the collection — and variables.json stays optional. On the riscv64 lane the guest-side truth lives in the guest's own test/sys_info.txt, which carries only the pin lines, never the host uname. The riscv64-nemu lane's extras are its run meta (meta.json) and the deploy meta (meta.deploy.json — corpus compiler, pinned inputs, image/rootfs sha256s), and its versions.txt gains a # nemu section (binary path, HEAD, describe --always --dirty, sha256); those two metas are the authoritative provenance record there. Since the venue's scratch-tree rebuild, a clean bench checkout no longer carries a spurious -dirty: the suffix now means the tree the image or corpus really came from was uncommitted, and a deploy that leaves the submodule dirty is a real edit. A lane's "current" stamp — what the lane-comparison tool selects by default — is the newest directory under results/<lane>/ that carries a versions.txt at its top; the pre-restamp relocation to retired-<pin>/ subdirectories is therefore inert to selection.

Trust boundary

The corpus is trusted code from a trusted source, but adversarial by design. The host lanes execute it unsandboxed with the invoking user's privileges — deliberately, and only on this workstation; the virtual-machine lanes are isolated by their disposable qemu guests, each booted -snapshot from its pinned image. The riscv64-nemu lane is a third model: no corpus instruction executes as a host process (NEMU interprets every one) and the guest's devices are NEMU's models over the image the deploy assembled, so its host surface is the NEMU binary and the lane's build files rather than the corpus. Do not repoint a host lane at an untrusted registry or corpus without adding isolation first.
