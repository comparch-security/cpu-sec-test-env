Architecture

The environment is a single dispatcher around one mutable workdir. The Makefile is the entry point (make ARCH=<lane> …); it reads the few values its recipes need from env.sh and dispatches to scripts/<lane>/ (the x86_64 lane is implemented inline in the Makefile). The benchmark submodule is the shared resource every lane mutates in turn — which is why every lane entry point takes a lock.

The lane lock

Every lane entry point that mutates the bench worktree — the run and clean paths, and the corpus-staging deploy legs — takes an advisory flock on build/.lane.lock and writes the lane name into it; a second concurrent lane fails fast with lane busy: <holder> holds build/.lane.lock (dump is the deliberate exception: it takes no lock). Every lane run body is wrapped in an EXIT trap that, on every outcome except a timeout, collects the lane's artifacts into results/<lane>/<UTC-stamp>/, runs make -C benchmark clean and asserts the submodule is clean. A run that hits its timeout (exit 124) aborts without publishing anything.

Pins

All pins live in env.sh: the bench commit, the toolchains, qemu, the guest kernel and busybox, the NEMU checkout and commit, cheribuild and the CHERI images, the roots and the timeouts. The Makefile and the lane scripts read them; nothing else hard-codes them. The Makefile refuses to run with an empty timeout or an empty build root rather than let a shell command fail at the wrong moment; the x86_64 deploy re-checks that the submodule's HEAD equals the pinned bench commit, and the riscv64-nemu lane's deploy and run both re-check that equality plus the submodule's cleanliness, alongside the NEMU checkout's own pin.

Deploy and the derived registry

The system lanes' deploy stages what their run needs: the riscv64 lane builds a byte-reproducible kernel + busybox + rootfs image, and the CHERI lanes build their emulators and pinned disk images (a cold deploy is a world build); the host lanes' prepare builds only the scheduler, and the corpus is compiled on demand during the run. Deploy also derives the lane's registry — scripts/common/derive_registry.py declares per-lane skips and expected failures at deploy time, so the platform caveats are derived, never hard-coded in the bench. The same step writes manifest.json: the corpus as deployed, the per-unit digests and the declared expectations. The riscv64-nemu lane is the deliberate exception: its deploy drives the bench's own platform scripts (benchmark/platform/riscv64-nemu-linux/), which derive their runset registry themselves, so derive_registry.py is not in that path — the lane's completeness gate compares the run's record set against that deployed registry instead.

The opcode-extraction shim

The bench's per-function opcode extraction disassembles a freshly built binary with an objdump. Every lane whose scheduler builds cross-target units puts a shim directory first on PATH (scripts/common/shim.sh) so that call resolves to the lane-appropriate cross tool rather than the host's single-target binutils; the CHERI lane points the same shim at the CTSRD SDK's CHERI-capable riscv64cheri-objdump, whose bin directory is deliberately off PATH.

Results and provenance

Each published stamp carries results.json and results.dat (the scheduler's record set and its report), versions.txt — the host-provenance record: the env.sh pins, the dpkg versions of the prerequisite packages and the host uname — and lane-specific extras (runtime variables, boot logs, guest status). On the riscv64 lane the guest-side truth lives in the guest's own test/sys_info.txt, which carries only the pin lines, never the host uname. The riscv64-nemu lane's extras are its run meta (meta.json) and the deploy meta (meta.deploy.json — corpus compiler, pinned inputs, image/rootfs sha256s), and its versions.txt gains a # nemu section (binary path, HEAD, describe --always --dirty, sha256); those two metas are the authoritative provenance record there, because the venue's guest-side # Bench tree line always reads <pin>-dirty — a bench-side artifact of its corpus staging (see the README caveats).

Trust boundary

The corpus is trusted code from a trusted source, but adversarial by design. The host lanes execute it unsandboxed with the invoking user's privileges — deliberately, and only on this workstation; the virtual-machine lanes are isolated by their disposable qemu guests, each booted -snapshot from its pinned image. The riscv64-nemu lane is a third model: no corpus instruction executes as a host process (NEMU interprets every one) and the guest's devices are NEMU's models over the image the deploy assembled, so its host surface is the NEMU binary and the lane's build files rather than the corpus. Do not repoint a host lane at an untrusted registry or corpus without adding isolation first.
