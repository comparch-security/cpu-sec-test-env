Lanes

The per-lane reference: what each lane executes, what its deploy and run do, and which of its pins are load-bearing. Operator-facing setup and the caveat ledger live in README.md; this page is the maintainer's view. Every pin named here lives in env.sh — treat that file as authoritative; this page explains why each lane's pins matter.

x86_64 — the reference lane

deploy is validation only: it checks the host toolchain and that the benchmark submodule's HEAD equals the pinned bench commit. run builds the bench and runs the scheduler natively; the trap publishes results.json, results.dat and variables.json.

aarch64 (+ pa / bti / mte)

prepare.sh builds the scheduler as a host binary for the aarch64 target, plus the objdump shim and the sys_info header; the test binaries are compiled during the run by the scheduler's own child makes with the cross toolchain, and run.sh executes them through the kernel's binfmt_misc handler under qemu-aarch64 — the bench's RUN_PREFIX is an environment injection, not a command prefix, so binfmt is the execution route. The programmatic variant flags (enable_aarch64_pa, _bti, _mte) select one variant at a time and publish under results/aarch64-<variant>/. The lane puts its shim directory first on PATH and logs the resolved extraction tool at run start.

riscv64

deploy builds the guest from pinned sources: the kernel (sha256-verified tarball; the lane's fragment forces userspace vector default-on), a static busybox, and a byte-reproducible rootfs image — identity pins for the build metadata, normalized mtimes, LC_ALL=C ordering and a device-independent cpio archive. run boots the image under qemu-system-riscv64 (-M virt, OpenSBI's default firmware) with the pinned rva23s64 CPU model — every executable the distro cross toolchain links declares the RVA23U64 profile, so a narrower model would be a latent illegal instruction inside the guest's own libc — and exports a share directory to the guest over virtio-9p (the result stamp itself is created afterwards, from what the guest left there); the guest init runs the prebuilt corpus and copies its results back. There is no console parsing and no dump target: the binaries live inside the guest image.

riscv64-nemu

The bench's own NEMU venue, wrapped as a lane. prepare.sh takes the lane lock, then preflights in one block before any build: the bench submodule at the pinned commit and clean (a leaked registry swap is named together with its deferral), the resolved NEMU_BIN, and the NEMU checkout's HEAD against NEMU_COMMIT — never the binary's provenance, which is recorded instead (path, describe --always --dirty, sha256) and compared run-to-run. NEMU_DIR/NEMU_BIN are a relative-default pair resolved against this repo's root. The deploy then runs the venue's own build-corpus.sh and build-image.sh with OUT under build/riscv64-nemu/, unsetting ARCH/MAKEFLAGS first so the scheduler's child makes do not inherit this dispatcher's lane name, and records the runset it built. run.sh requires that runset (an explicit mismatch fails naming both), boots the image under the pinned NEMU with NEMU_TIMEOUT forwarded so the platform diagnoses its own boot timeout first, and supervises both legs as their own sessions with the lane-lock fd closed (9>&-), so the lane's own bound owns the kill rather than the outer timeout: the TERM/124 kill sweeps the whole session (sid == $LEG_PID, SIGKILL for whatever survives), which reaches the platform's inner timeout NEMU group too, so no descendant outlives the lane or holds its lock. Results are extracted by parsing the guest console (===CSB-…=== markers), so boot.log is part of every non-timeout stamp — the run dir's own log when one was created, else the lane's platform log copied under that name. The completeness gate compares the run's record set against the deployed runset's derived registry before any result file reaches the stamp: a gate failure publishes a boot.log + versions.txt evidence stamp only, and a timeout publishes nothing. The corpus never executes as host code — NEMU interprets every guest instruction, and the guest's devices are NEMU's models over the image the deploy assembled.

cheri_riscv64

The guest is a pinned, sha256-verified purecap CheriBSD disk image. Boot is two-stage by necessity: the pinned bbl firmware (riscv-pk) loads into M-mode and jumps to an external -kernel; the CPU pin rv64,sstc=off is load-bearing (the pinned firmware never sets menvcfg.STCE, and without the pin the guest panics at clock init). The corpus is handed in over a read-only virtio-9p share and results are collected from a writable one; a host-side console driver logs into the serial pty, synchronises on echo tokens, and drives the run. Deploy splits its timeouts deliberately: the cheap legs carry the lane deploy timeout while the emulator and image builds carry the generous CHERI build timeout — an outer lane-deploy timeout would fire in the middle of a world build.

aarch64-morello

The same class of pinned image, booted UEFI-style: edk2-aarch64-code.fd plus loader(8) reads the kernel from the disk image, so this lane takes no -kernel. The machine is virt with GICv3; the corpus and results travel over the same two virtio-9p shares, driven by the same console driver.

Do not simplify

The two CHERI lanes do not boot the same way, on purpose. The riscv64 CHERI guest needs the firmware, the external kernel and the sstc=off CPU pin together — there is no disk-only boot transition that can succeed. And the riscv64 lane's CPU model is a profile decision, not a preference: it follows the cross toolchain's architecture tag, not the lane author's taste.
