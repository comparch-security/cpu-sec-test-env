Lanes

The per-lane reference: what each lane executes, what its deploy and run do, and which of its pins are load-bearing. Operator-facing setup and the caveat ledger live in README.md; this page is the maintainer's view. Every pin named here lives in env.sh — treat that file as authoritative; this page explains why each lane's pins matter.

Lane Target Execution path Host prerequisites
x86_64 native Host processes, directly host g++ + objdump
aarch64 (+ pa/bti/mte) aarch64 binfmt_misc → qemu-aarch64 registered binfmt handler (root-only), qemu-user, cross gcc-13, host g++
riscv64 riscv64 System qemu guest; results over virtio-9p qemu-system-riscv + qemu-system-data, cross gcc-13
riscv64-nemu riscv64 (emulated) A Linux guest interpreted by XiangShan NEMU; results parsed from the guest console a built ../NEMU interpreter (NEMU_DIR/NEMU_BIN), cross gcc-13

aarch64-morello Morello purecap Morello qemu guest; 9p shares for corpus and results the five cheribuild packages, host g++

x86_64 — the reference lane

deploy is validation only: it checks the host toolchain and that the benchmark submodule's HEAD equals the pinned bench commit. run builds the bench and runs the scheduler natively; the trap publishes results.json, results.dat and variables.json.

aarch64 (+ pa / bti / mte)

prepare.sh builds the scheduler as a host binary for the aarch64 target, plus the objdump shim and the sys_info header; the test binaries are compiled during the run by the scheduler's own child makes with the cross toolchain, and run.sh executes them through the kernel's binfmt_misc handler under qemu-aarch64 — the bench's RUN_PREFIX is an environment injection, not a command prefix, so binfmt is the execution route. The programmatic variant flags (enable_aarch64_pa, _bti, _mte) select one variant at a time and publish under results/aarch64-<variant>/. The lane puts its shim directory first on PATH and logs the resolved extraction tool at run start. The run recipe takes the lane lock once around both legs and passes LANE_LOCK_INHERITED=1: the scripts honour the marker only when the inherited descriptor verifiably is the held lane lock, then close it so no lane child inherits it. Both scripts also assert the submodule's HEAD against the pin before doing anything, and the collector treats results.json/results.dat as required and parseable (variables.json optional) and stamps the run's final rc.

Every aarch64-family stamp before 2026-10-25 is a non-execution record. env.sh used to export QEMU_VERSION, and this venue's qemu-aarch64 reads that name itself: for any value it printed its version banner and exited 0 before parsing -cpu and before loading a guest, so every case of every stamp from 2026-10-13 to 2026-10-24 "ran" as a banner print and the scheduler recorded 0. The version pin is renamed (QEMU_PIN_VERSION) and no longer exported, and prepare.sh's binfmt smoke asserts the guest loader's own output rather than an exit code, so a zero-execution route fails the deploy instead of publishing a stamp.

The pa and mte variants each request a CPU model, and for pa the request is load-bearing. Both pin QEMU_CPU=max — the venue's default model plus PAuth. max is not the default: left unset, this qemu-aarch64 behaves as max,pauth=off (byte-identical HWCAP), so the plain lane and bti need no request while the pa lane's retaa epilogue (-march=armv8.3-a+pauth -mbranch-protection=pac-ret) raises SIGILL without one — its first really-executing stamp (dated snapshot, 2026-10-25) drowned in 256+4, and the pinned request removed that class entirely. prepare.sh executes a lane-representative build under the request at deploy — a PAC-ret probe for pa, an -fsanitize=hwaddress program for mte — and cross-checks each such smoke's class flags against the pinned benchmark/Makefile's own variant block (failing closed when the block or its flag lines cannot be read), so the smokes prove the build the corpus will actually get rather than a paraphrase of it — a request the venue cannot honour fails the deploy rather than every case. The mte smoke's acceptance is two-outcome on purpose: the program's own line is the primary proof, and the runtime's 99 with a sanitizer report is the pre-output fallback, because qemu-user cannot run the sanitizer's LeakSanitizer leg (a clean exit is not this venue's shape). The bti smoke builds an xpaci-bearing binary under the request and requires it to execute — the census of the built binary must find xpaci (so the leg cannot pass vacuously), and the guest must run it: the class's -march=armv8.5-a implies PAuth, and a PAuth-less model turns the bench's STRIP_PAC() into a SIGILL (this is exactly what the first post-f9e4ba7 bti stamp caught — five records at 260 before the request was pinned). The mte lane's old spelling max,mte=on was rejected outright by this qemu-aarch64 (no model has that property) and never reached a guest; under the current request the guest reports HWCAP2_MTE, a tag check on a PROT_MTE mapping faults with si_code 9 (the RT_SICODE_MTESERR-class predicate), and the -fsanitize=hwaddress build aborts with the HWASan runtime's 99 on the tag-touching cases — the mte stamps are the only aarch64 stamps carrying that class. Each stamp records both the request and the observation (# CPU request: beside # CPU observation:), so a stamp says what was in effect, never what was intended. The three variant lanes (pa, bti, mte) each request the same model, QEMU_CPU=max — the venue's default plus PAuth — under three different names in env.sh, because the bti class needs it as much as pa does: its -march=armv8.5-a implies PAuth, and the bench's STRIP_PAC() compiles to xpaci, which traps on a model without FEAT_PAuth (the fault is the PAuth the -march drags in, not the BTI hints). Only plain aarch64 is request-less: it clears an ambient QEMU_CPU outright rather than inheriting one, and both scripts drop an inherited QEMU_VERSION, so the recorded unset is the truth and not an assumption.

The pa class's RA-offset calibration runs under PAC-ret. The bench's RA-offset producers once scanned the stack with a raw frame compare, which cannot match a PAC-signed saved LR: the producer stored nothing, and ten return-hijack records fell back to their documented guard and delivered the shared 1 — precondition failures their declared expectation hid from a per-record classification. The bench fix has the producer derive and store a real offset under this lane's flags, so those ten records execute their measurement instead of skipping it; the lane's variables.json carries the stored offsets (stack-offset-v-p-g0/-g1) and cfi-return-without-call delivers its declared crash code. A stamp whose variables.json lacks the offsets or whose ten records still read the shared guard is evidence of a regression, not of the limitation.

riscv64

deploy builds the guest from pinned sources: the kernel (sha256-verified tarball; the lane's fragment forces userspace vector default-on), a static busybox, and a byte-reproducible rootfs image — identity pins for the build metadata, normalized mtimes, LC_ALL=C ordering and a device-independent cpio archive. run boots the image under qemu-system-riscv64 (-M virt, OpenSBI's default firmware) with the pinned rva23s64 CPU model — every executable the distro cross toolchain links declares the RVA23U64 profile, so a narrower model would be a latent illegal instruction inside the guest's own libc — and exports a share directory to the guest over virtio-9p (the result stamp itself is created afterwards, from what the guest left there); the guest init runs the prebuilt corpus and copies its results back. There is no console parsing and no dump target: the binaries live inside the guest image.

riscv64-nemu

The bench's own NEMU venue, wrapped as a lane. prepare.sh takes the lane lock, then preflights in one block before any build: the bench submodule at the pinned commit and clean — the deploy's two invariants (HEAD equals BENCH_COMMIT, tree clean). The venue cross-builds its corpus in a scratch tree under out/build/<runset>/tree and never writes the tracked registry, so any dirt in the submodule is a real edit and is named as such; a failing git is refused as unverifiable, never read as clean. The preflight also checks the resolved NEMU_BIN, and the NEMU checkout's HEAD against NEMU_COMMIT — never the binary's provenance, which is recorded instead (path, describe --always --dirty, sha256) and compared run-to-run. NEMU_DIR/NEMU_BIN are a relative-default pair resolved against this repo's root. The deploy then runs the venue's own build-corpus.sh and build-image.sh with OUT under build/riscv64-nemu/, unsetting ARCH/MAKEFLAGS first so the scheduler's child makes do not inherit this dispatcher's lane name, and records the runset it built. run.sh requires that runset (an explicit mismatch fails naming both), boots the image under the pinned NEMU with NEMU_TIMEOUT forwarded so the platform diagnoses its own boot timeout first, and supervises both legs as their own sessions with the lane-lock fd closed (9>&-), so the lane's own bound owns the kill rather than the outer timeout: the TERM/124 kill sweeps the whole session (sid == $LEG_PID, SIGKILL for whatever survives), which reaches the platform's inner timeout NEMU group too, so no descendant outlives the lane or holds its lock. Results are extracted by parsing the guest console (===CSB-…=== markers), so boot.log is part of every non-timeout stamp — the run dir's own log when one was created, else the lane's platform log copied under that name. The completeness gate compares the run's record set against the deployed runset's derived registry before any result file reaches the stamp: a gate failure publishes a boot.log + versions.txt evidence stamp only, and a timeout publishes nothing. The corpus never executes as host code — NEMU interprets every guest instruction, and the guest's devices are NEMU's models over the image the deploy assembled.

cheri_riscv64

The guest is a pinned, sha256-verified purecap CheriBSD disk image. Boot is two-stage by necessity: the pinned bbl firmware (riscv-pk) loads into M-mode and jumps to an external -kernel; the CPU pin rv64,sstc=off is load-bearing (the pinned firmware never sets menvcfg.STCE, and without the pin the guest panics at clock init). The corpus is handed in over a read-only virtio-9p share and results are collected from a writable one; a host-side console driver logs into the serial pty, synchronises on echo tokens, and drives the run. Deploy splits its timeouts deliberately: the cheap legs carry the lane deploy timeout while the emulator and image builds carry the generous CHERI build timeout — an outer lane-deploy timeout would fire in the middle of a world build.

aarch64-morello

The same class of pinned image, booted UEFI-style: edk2-aarch64-code.fd plus loader(8) reads the kernel from the disk image, so this lane takes no -kernel. The machine is virt with GICv3; the corpus and results travel over the same two virtio-9p shares, driven by the same console driver.

Do not simplify

The two CHERI lanes do not boot the same way, on purpose. The riscv64 CHERI guest needs the firmware, the external kernel and the sstc=off CPU pin together — there is no disk-only boot transition that can succeed. And the riscv64 lane's CPU model is a profile decision, not a preference: it follows the cross toolchain's architecture tag, not the lane author's taste.
