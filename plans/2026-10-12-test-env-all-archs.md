## Summary

**Problem.** `cpu-sec-test-env` must become *the* environment that builds and runs `cpu-sec-bench` on every supported architecture, so per-arch bench fixes can be validated under emulation. Today the repo is a 2020-era shell: the riscv64 lane points into the deleted `riscv-linux-sdk` submodule, the x86_64 `run` target calls a bench target that has not existed since 2022, and there are no aarch64/CHERI lanes at all. The bench side has finished its work for this purpose: submodule commit `c2c7039` adds the scheduler-owned `1025` *not run* code (platform `skip` lists, build failures), `CSB_TARGET_ARCH`, and the `disable_independent_assembly` opt-out that lets a port build before its `.asm` is translated.

**Approach — three lanes end-to-end, CHERI probed, everything pinned.**

```
HOST (x86_64, Ubuntu 26.04)                      GUEST
┌─────────────────────────────────────────────────────────────────────────────┐
│ x86_64 lane   make → ./run-test exhausted-run ────────────── native process │
│ aarch64 lane  make -B run-test ARCH=aarch64 CXX=g++ (host binary)           │
│               MAKEFLAGS='ARCH=aarch64 CXX/aarch64-…-13 enable_aarch64_x=yes'│
│                                        └─ binfmt_misc ─→ qemu-aarch64 ──────│
│                                            (QEMU_CPU=max[,mte=on])         │
│ riscv64 lane  corpus(143 built + 2 expected-fail) → Image+busybox+cpio ─┐   │
│               qemu-system-riscv64 -cpu rva23s64 -M virt -bios default ───→  │
│                                        └─ 9p share ←── results.json/.dat     │
│ cheri lane    cheribuild @db2f036 → CHERI-LLVM/Morello-LLVM → dialect probe │
└─────────────────────────────────────────────────────────────────────────────┘
```

1. **Top-level Makefile as lane dispatcher.** `make ARCH=<lane> [enable_* flags] deploy|run|clean|dump`, all pins in `env.sh`; the x86_64 lane is fixed to `make -C benchmark` + `./run-test exhausted-run`; the riscv-linux-sdk block is deleted. One lane runs at a time (advisory lock), and every lane — success or failure — copies its artifacts out and leaves the submodule clean.

2. **The corpus problem, solved with zero bench changes.** The bench scheduler builds each `(program, conf-macro map)` unit into the single path `test/<program>`, overwriting it when the map changes, and `no-make` runs whatever file is present. The registry has 246 records over 103 programs = **145 build units over 25 distinct maps**; 17 programs carry 3–4 variants, so a naive prebuilt corpus would silently run the wrong binary for **68 records** (measured; a single-variant deployment plus honest `skip` would lose exactly those 68). The bench's own corpus-mode plan (`benchmark/tmp/plans/2026-10-11-riscv64-nemu-linux-platform.md`) is unimplemented and its env-side half is explicitly this repo's job. Because a record never spans maps across its argument indices (verified: 0 such records), a **deploy-time derived registry** can give every unit its own program name — `<prog>__<key>`, key = FNV-1a-32 of the canonical sorted `K=V` map string, empty map `811c9dc5`, exactly the bench plan's own scheme so a future bench-side corpus mode replaces this 1:1 — and cover all 246 records in one guest run. Of the 145 units, **143 are staged**; the two programs that cannot link under `disable_independent_assembly` (`cfi-return-to-peer-asmfunc`, `cfi-return-to-parent-non-call-site-by-asmfunc`; deferred issue `indepassembly-return-site-untranslated`) are the manifest's `expected_failures` and their records are declared `skip` with a reason in the derived registry — any other build failure aborts the deploy. The corpus build also carries the **one run-time side artifact** the registry references but no unit file provides (`test/acc-read-func-func-opcode.tmp`, the opcode word `acc-read-func` is given as an argument), derived from the registry's own argument strings and declared in the manifest. The corpus is built by issuing **the scheduler's own command** per unit, so no variant knowledge is duplicated beyond `configure.json` itself.

3. **riscv64 guest built from pinned sources.** The issue's "our pinned kernel+initramfs (shared with the NEMU/XiangShan work)" does not exist: `XiangShan/ready-to-run/linux.bin` is a NEMU-only payload (xiangshan FDT, UARTLite console, no virtio/mmc/ext4 drivers, rootfs = `dev/` + a static `/init`), the NutShell bbl image's rootfs is glibc 2.29 (older than the ≥2.34 symbol versions the toolchain's binaries need), and the workspace sysroot has libraries but no shell or init. The lane therefore builds Linux 6.18.56 from the kernel.org tarball (sha256-pinned, `KBUILD_BUILD_*` pinned for byte-reproducibility) with a committed qemu-virt config fragment (revised 2026-10-13: ≥ 6.5 is a hard floor — the apt cross glibc is RVA23U64 machine code and its memcpy executes vector instructions, while the original 6.1.83 pin predates RISC-V userspace vector support entirely; the fragment now forces `RISCV_ISA_V` + `RISCV_ISA_V_DEFAULT_ENABLE`), busybox 1.36.1 (sha256-pinned, `SOURCE_DATE_EPOCH`-pinned) statically linked, and a glibc rootfs whose library set is derived from `readelf -d` NEEDED closures rather than guessed. The guest runs `./run-test no-make exhausted-run` and copies its results over a virtio-9p share (mounted `cache=none`, with `sync` twice and a status marker before poweroff) into the host results directory — no console parsing, no privileges.

4. **aarch64 runs through binfmt, not `RUN_PREFIX`.** `RUN_PREFIX` in the bench is an *environment-variable injection* (`add_extra_run_prefix` splits it into `envp` entries), not a command prefix, so qemu-user is reached the kernel's way: the `qemu-user-binfmt` handler executes every aarch64 ELF (the scheduler stays a native host binary; `CSB_TARGET_ARCH=aarch64` is baked from `ARCH` by the Makefile itself at build time). The sysroot is the apt cross sysroot pinned in `env.sh`; the MTE variant's `-cpu max,mte=on` rides `QEMU_CPU`, inherited through binfmt. The four aarch64 lanes differ because the lane's `enable_aarch64_<variant>=yes` is appended to the scheduler's `MAKEFLAGS` (command-line strength), and each lane's sys-info block records it.

5. **CHERI lanes probed, not built.** cheribuild at a pinned commit builds CHERI-LLVM (the `llvm` target) and Morello-LLVM (`morello-llvm`); the probe assembles both dialects **twice each** — the `.asm` as-is (which carries the known untranslated x86 `assembly_return_site`) and with the deferral's ready translation text, vendored into this repo — with `-march=rv64gcxcheri -mabi=l64pc128d` and `-march=morello -mabi=purecap`, recording raw commands, exit codes and stderr as the verdict. Full bring-up (CTSRD-QEMU, Morello-QEMU, CheriBSD purecap images) is the deferred follow-up.

**Trust boundary.** The corpus consists of deliberately-attacking binaries built from the pinned bench at `c2c7039`; they are trusted code from a trusted source, but they are adversarial by design. The host-run lanes (x86_64, aarch64) execute them **unsandboxed with the invoking user's privileges — deliberately, and only on this workstation**; the riscv64 lane executes them inside a disposable qemu VM, which is the isolation for that lane. No host lane may be repointed at an untrusted registry or corpus without adding isolation first (recorded so a future operator does not assume sandboxing that is not there).

**Alternatives considered and rejected.** *Naive prebuilt corpus* — silently mis-runs 68 records. *Single-variant deploy + skip the rest* — same 68-record loss. *Per-pass booting, one map group per boot* — correct but N boots and a host-side merge; the derived registry is one boot with no merge. *Adding corpus mode to the bench* — the bench is frozen at `c2c7039` and env-side work is this repo's by design; our unit keys match the bench plan's so the two can converge later. *Compiler inside the guest* — 10s of MB and divergent; the host builds everything. *qemu-user as the riscv64 venue* — cheap (sysroot already installed) but skips the booted-Linux venue the issue asks for; kept only as an optional future lane. *Reusing the on-disk images* — wrong machines and a glibc too old. *Rootless .deb extraction* — rejected in favour of one apt install, which is also the only way to get a binfmt handler.

**Explicitly out of scope.** The per-arch bench test fixes and the `.asm` translation itself (bench repo, deferred); spec2017; full CHERI/Morello emulator + guest bring-up (deferred); NEMU/XiangShan venue integration (this plan's riscv64 image is deliberately qemu-virt-only per decision, not NEMU-bootable); Windows/MSVC; per-case timeouts (bench deferral); sandboxing for host lanes (see Trust boundary).

## Rollback

- **Single consolidated commit (user decision 2026-10-13).** Per-step commits are dropped: the coder's deployed settings deny `git commit` (round 5's three attempts were refused, and the denial also ended its round). Each step stages its files (`git add`, explicit paths only) once its checks are green; the work accumulates in the worktree and the plan's final `/update-and-commit` makes the one commit. Per-step `git revert` granularity is therefore unavailable — recovery is reverting that single commit or resetting generated state (next bullet). The pre-step commit `4eb5c27` and Step 1's `08e64de` landed before this decision and stay as they are.
- **Pre-existing staged changes.** The already-staged `riscv-linux-sdk` removal (`.gitmodules` + gitlink) and the unstaged `benchmark` gitlink bump are committed **first, as their own commit**, before Step 1 — the plan's commit scope therefore starts from a clean index, and a Step-1 revert cannot resurrect the dangling SDK block.
- **Generated state is disposable.** `build/` and `results/` are gitignored; a failed or abandoned lane is recovered by `make ARCH=<lane> clean` plus deleting `build/<lane>/`, never by git operations. The bench submodule is restored by `git -C benchmark checkout c2c7039 && git -C benchmark clean -fdx` (its only mutable state is gitignored build output).
- **The one irreversible action** is the bench push prerequisite (`c2c7039` to the public bench repo) — it is additive and cannot break the test-env repo, but it is public: it happens only on the user's explicit go-ahead.
